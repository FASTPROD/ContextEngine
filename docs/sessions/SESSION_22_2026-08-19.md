# Session 22 — 2026-08-19 — the cost collector, and two gates that were never called

**Scope**: built `contextengine cost` from Claude Code's own transcripts, then audited every
CE guard rail by executing it. Two gates were enforcing nothing.

Continues from [SESSION_21](SESSION_21_2026-08-16.md).

## A. The format had a 2.8x trap in it

Instruction was "don't assume the format — inspect real files first." Doing so paid immediately.

One assistant `message.id` is written across **several JSONL lines** (one per content block:
thinking, text, each `tool_use`), and **every line repeats the same `usage` object**. Summing
per line reported **624,873 cache_read tokens where the true figure was 225,183** — 2.8x over,
and 4.6x on `cache_creation`.

Verified invariants over **1,609 message ids in 126 files** before relying on them:

| Invariant | Result |
|---|---|
| `input`/`cache_creation`/`cache_read` constant within a `message.id` | **0 exceptions** |
| `output_tokens` monotonically increasing within an id | **0 exceptions** — so max is the final count |
| one `agentId` per file | **0 files with more** |

Locked as `[TRANSCRIPT-DEDUP-BY-MESSAGE-ID]`. A cost report that overstates by 3x is worse than
none: it gets disbelieved once, then ignored forever.

**Second trap: terminal state is not the last line.** 2,090 of 2,310 transcripts end on a `user`
line — the tool_result for the agent's own final `StructuredOutput` call. Reading the last line
classified 2,146 healthy agents as "no report" and would have made `fanout_without_canary` fire
on every workflow ever run. Locked as `[AGENT-REPORTED-IS-NOT-LAST-LINE]`. Correct classification
across the corpus: **2,285 reported / 19 capacity_exhausted / 3 api_error / 2 no_report / 1 output_cap**.

## B. Cost, not tokens — and the two stories that disagree

Weighted cost is `input*5 + cache_write*6.25 + cache_read*0.5 + output*25` per million (Opus 5).
Rates live in `.contextengine/policy.json` → `agent_cost.pricing`, never hardcoded
(`[PRICING-LIVES-IN-POLICY]`). No `*` catch-all on purpose: an unknown model reports as
**UNPRICED**, never as $0.

The volume ratio and the cost ratio point in opposite directions, which is the whole point:

| Run | Output by volume | Cache reuse | Valued cost | Verdict |
|---|---|---|---|---|
| `wf_67cbce22` (30 agents) | 1.8% — *looks alarming* | 8.3x | $34.78 vs $120 uncached | **healthy** |
| `wf_f676d824` (722 agents) | 7.5% — *looks better* | **0.4x** | $209, **68% on cache WRITES** | **pathological** |

So `context_burn` fires on **cache inefficiency, tool-call inflation, and per-agent cost** — and
deliberately **never** on a low output/volume ratio (`[BURN-IS-COST-WEIGHTED-NOT-VOLUME]`). Firing
on the ratio would flag every well-cached run and burn the alert budget, the exact failure the
`[DRIFT-HEURISTICS]` LOCK exists to prevent.

`fanout_without_canary` is a **time ordering**, not an outcome (`[CANARY-IS-A-TIME-ORDERING]`):
it counts agents that started before the earliest sibling *finished*. A completed 300-agent run
has 300 reports and was still un-canaried.

## C. The bug that hid inside the failures it was measuring

First run showed `⚠ 2.2M tokens UNPRICED`. Chasing it found a real defect.

Claude Code writes client-side notices ("You're out of usage credits", "API Error: …") as
assistant messages with model `<synthetic>` and **all-zero usage**. They land **last**, and the
collector took each agent's model from its last assistant message — so **every capacity-killed
agent was tagged `<synthetic>`**, and since that model has no price, its entire real consumption
was dropped.

The cost of the failure was missing from the report whose job is to surface that failure.
`wf_41771d7b` read **$29.78; the true figure is $42.70 — a 43% understatement**, concentrated
precisely on the 15 agents that died. Fixed by attributing tokens **per message model**
(`[PRICE-PER-MESSAGE-MODEL-NOT-PER-AGENT]`), with a regression test.

This is session 21 §J's rule earning its keep: the reading that lowered risk was the wrong one.

## D. Billing nuance: the dollars are notional

So `contextengine cost` prints **three panels, never one** — volume, valued cost (labelled
NOTIONAL), and intensity (agents, tool calls, duration, deaths) as the capacity proxy. On a
subscription the scarce resource is the usage window, and the capacity signal is directly
observable: dead agents end with *"You're out of usage credits."*

### E1. `commit_message_required` was enforcing nothing

The rule type, its CLI subcommand and its tests all existed and all passed. `contextengine init`
installed **pre-commit and post-commit only**. Proven by execution: in a fresh repo with a
`severity: block` rule on `server/deploy.sh`, committing that file with a non-compliant message
**succeeded**. It worked in *this* repo solely because a commit-msg hook had been installed by
hand — so the author's own machine was the one place the gap was invisible.

Fixed: `generateCommitMsgHook()` + install in `init` (`[COMMIT-MSG-HOOK-MUST-BE-INSTALLED]`).
It cannot live in pre-commit — git does not populate the message file until after pre-commit
returns. Re-proven: non-compliant commit now blocked, compliant commit and unrelated files pass.

### E2. The canary covered the human path, not the agent path

`[SCORE-CANARY]` was wired on the CLI only. MCP `score_project` — the path Claude Code scores
through — had **zero** call sites, so a drifting scorer would be caught when a human typed the
command and missed entirely when an agent called the tool. Same shape as session 21 §H2. Fixed
as `[SCORE-CANARY-COVERS-EVERY-SCORER]`.

### E3. Two of my own reads needed the second check

Both would have been false findings, both caught by re-running a different way:

- *"commit-message gate blocks valid messages"* — I passed `--message-file`; the CLI takes a
  **positional** arg. It fell back to an empty message and blocked correctly.
- *"`check_ports` is ungated on the CLI"* — there is no `check-ports` CLI command. Unknown
  commands fall through to starting the MCP server, which is what I measured.

Also noted: `audit-verify` "exit=0 on a FAILED chain" was a pipeline artifact (`$?` of `head`).
Measured directly it is **2**. Three shallow reads, three retractions — the same discipline
session 21 §J paid for.

## H. 2.5.2, two absent verdicts, one on the bedrock (2026-08-20)

Both follow-ups closed here are the same shape as §G, at different layers: a branch meaning
*"I could not determine this"* returning a plausible action or value instead.

### H1. A typo started a server

`cli.ts` dispatched on a long if/else chain ending in `else { import("./index.js") }`, so **any**
unrecognised token started a stdio MCP server waiting on stdin. No error, no exit code, no
output, just a hang. `contextengine scor`, `contextengine --version` and a renamed subcommand all
behaved that way.

It had already cost a wrong finding: §E3 recorded *"`check_ports` is ungated on the CLI"*. There
is no `check-ports` command at all. What got measured was a server booting.

Fixed as `[UNKNOWN-COMMAND-MUST-NOT-START-A-SERVER]`: unknown token names itself, suggests the
nearest command, exits 1. The server starts only on a bare invocation or the explicit `serve`
alias, and every launcher on this machine uses the bare form. `--version` now exists.
`KNOWN_COMMANDS` in `src/cli-commands.ts` is the single source of truth, and a parity test fails
if it drifts from the literals the dispatcher actually handles.

### H2. Rotation had to move history, because deleting it is what the verifier reports

The log was at **198 MB / 544,143 records**, growing 80,000/day, with no rotation path. The
reason it never got one is worth recording: the obvious implementation destroys the product.
`mv audit.log audit.log.1` makes the first record of the new file an **orphan**, and
`[VERIFY-FORK-IS-NOT-TAMPER]` classifies an orphan as deleted history, a hard failure. Scripted
logrotate would have turned a healthy chain into a permanent TAMPERED verdict.

`[ROTATION-MUST-NOT-ORPHAN-THE-CHAIN]`: a prefix moves into an append-only segment under
`audit-archive/`, and canonical history is *segments in order, then the live log*. Verification
is unchanged because the chain is still continuous.

Three findings came only from measuring, not from designing:

| Finding | LOCK |
|---|---|
| **Age does not bound size.** At 80k records/day a 30-day window still left **390,445** records live, and even 3 days left 205,422. Date retention alone would have shipped a feature that rotates and changes nothing. Added a record ceiling; whichever rule archives more wins. | `[DATE-RETENTION-DOES-NOT-BOUND-SIZE]` |
| **`push(...records)` overflows the stack** at 494,152 records. Every one of the 15 unit tests passed, all with chains of a few thousand. Found on the first real run, where post-rotation verify failed with *Maximum call stack size exceeded*. | `[NO-SPREAD-OVER-A-SEGMENT]` |
| **Both head readers returned genesis on an unparseable last line**, so a truncated record made the *next append* manufacture an orphan. The writer would have produced the log's hardest failure by itself. | `[UNREADABLE-HEAD-IS-NOT-GENESIS]` |

Ordering is archive-then-truncate (`[ROTATE-ARCHIVE-BEFORE-TRUNCATE]`), so the only reachable
crash state is a duplicated prefix, de-duped at the seam, never a lost one. Rotation refuses to
run on a chain that does not verify, and appends an `audit.rotate` record about itself.

**Real run:**

| | Before | After |
|---|---|---|
| live log | 198 MB, 544,143 records | **17 MB, 50,001 records** |
| archived | none | 494,152 records in `audit-0001.jsonl` |
| `audit-verify` | 544,143 ok, 66 forks | **544,154 ok, 0 altered, 0 missing, still exactly 66 forks** |
| detector hot path (`scanRecentEvents`) | 2,386 ms / 693 MB | **121 ms** |

That last row is the part that was not about disk: the drift detectors read the log on every
tick for a 5-minute window, so the whole history was being parsed to answer a question about the
last few minutes.

**Test strength was checked, not assumed.** Disabling segment reads fails 5 of the rotation
tests, including the zero-orphans assertion. A suite that passes both with and without the
feature would have proved nothing, which is §G1's lesson applied before writing the claim.
