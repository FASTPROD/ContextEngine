separate agent sessions had been bitten by `contextengine score` — its no-argument default was
a fleet-wide *write*. Also chased a reported pre-commit hook bug, which turned out not to exist.

## B. Fleet-wide scoring is now opt-in — LOCK `[SCORE-FLEET-IS-OPT-IN]`

`contextengine score` with no argument scored all 37 discovered projects **and wrote a
`SCORE.md` into every one of them**. The scan was harmless; the write was not. It dirtied 26
repositories, several of which auto-push to Google Drive on commit, so the noise propagated
off-machine before anyone noticed.

The mismatch is the whole bug: the blast radius of the default was the entire fleet, while the
intent behind typing it was almost always *"score the repo I am standing in."* Three separate
agent sessions made exactly that assumption.

| Command | Scores | Writes |
|---|---|---|
| `score` | current project (walks up to repo root) | that one project |
| `score <name>` / `score <path>` | that one project | that one project |
| `score --all` | all 37 | **all 37** |
| `--no-save` | as above | nothing |

`--all` combined with a project argument is now a hard error rather than a silently ignored
flag, and `--all` prints how many projects it is about to write into before doing it.

**The MCP `score_project` tool was deliberately left fleet-wide by default** — it never writes
`SCORE.md`, so it does not carry the hazard. The rule applied is that the *write* must be
asked for, not that the scan must be.

Evidence of the pre-existing damage, found while verifying: `PLANK.io`, `COMPR-app`,
`CROWLR.io` and `INVOK.fr` all had a modified `SCORE.md` timestamped `13:49` — before this
session's first score run. Left untouched; other people's repos, and the 26 dirty working
trees are the user's to clean up or commit.

## C. `score` accepts a path — LOCK `[SCORE-ACCEPTS-PATH]`

`contextengine score /Users/yan/Projects/PLANK.io` failed with:

```
❌ Project not found: "/Users/yan/Projects/PLANK.io"
Available: ..., PLANK.io, ...
```

— an error that named the project it claimed not to find, listed it among the available ones,
and pointed at a directory that plainly exists. The lookup only ever compared basenames, so the
directory was never inspected. Same shape as the bugs of Session 20, one layer up:
**"not in my name index" was reported as "does not exist"** — `[ABSENCE-IS-NOT-A-VERDICT]` at
the argument-parsing layer.

`resolveProjectDir()` now resolves names and paths alike, and a path that exists is a project
whether or not it sits under a configured workspace — which is what makes the tool usable
outside `~/Projects`. Name lookup runs *first* for bare tokens, so `score KONIVE.com` resolves
exactly as it did before (important: several project names contain dots, and one contains a
space).

Also added to the MCP tool, where it is strictly more accepting and changes no default.

## D. The reported hook bug does not exist

**Reported** (from the KONIVE session): the CE-generated pre-commit hook regenerates and
re-stages `SCORE.md` mid-commit, silently overwriting staged content, producing an empty commit.

**Checked before changing anything, as instructed. It does neither.**

`generatePreCommitHook()` in [src/cli.ts:238](../../src/cli.ts#L238) is ~70 lines that only
ever *read*: it `stat`s the mtime of `.github/copilot-instructions.md`, `SKILLS.md` and
`SCORE.md`, counts anything older than 4h as a violation, greps staged files for secret
patterns, and exits 0 or 1. There is no score invocation and no `git add` anywhere in it.

Verified three ways:

```
grep -n "git add|git stage|--amend"  KONIVE.com/.git/hooks/{pre,post}-commit  → NONE FOUND
grep -n "git add"                    src/cli.ts                               → NONE
```

The hook actually installed in `KONIVE.com` is an older 8.3 KB custom variant from 2026-06-08
(the current template is much smaller), and it too only calls `check_freshness`, which stats
candidate paths and warns. Neither hook writes, regenerates, or stages anything.

**No change made.** The empty commit in the KONIVE session has another cause — most likely `B`:
a bare `contextengine score` rewrote `SCORE.md` across the fleet, and a subsequent
`git commit SCORE.md` in a repo where the regenerated content was byte-identical produced
nothing to commit. That is consistent with the report's symptom without requiring a hook that
writes. Fixing `B` removes the mechanism either way.

Recorded rather than silently dropped: a bug report that does not reproduce is a finding.

## F. The review agents reproduced the bug on live repos — and found the vector

An adversarial review workflow (4 lenses × refutation) was run against the diff before
publishing, instructed to *"run the real CLI"*. It did — and while doing so **rewrote SCORE.md
across 9 real repositories**, plus wrote a bogus `~/Projects/SCORE.md`. The workflow was killed
mid-run, all 9 files backed up to the scratchpad, and every one reverted to HEAD. Fleet
verified back to **0 dirty SCORE.md**.

Embarrassing, and worth more than the review it interrupted, because the two writes had
*different causes* and both were real defects:

**F1. The 9 repos were written by npm's frozen 1.23.1, not by this build.** Their headers read
`42/94`, and root-level `copilot-instructions.md` was reported `Missing` — a 94-point rubric with
`.github/`-only doc lookup, i.e. pre-`[DOC-PATH-DUAL]`, pre-`[SCORE-ARITHMETIC-INVARIANT]`
behaviour from June. This build scores the same repo `4/6` on that check. The vector:

```
skills/opscontext/SKILL.md:45   npx @compr/contextengine-mcp score   # AI-readiness score
```

**The shipped skill package instructed agents to run the deprecated package name**, which npm
freezes at 1.23.1 — so following our own documentation downloads a June scorer and fleet-writes
with it. Ten call sites fixed, including three MCP-config blocks (`args: ["-y",
"@compr/contextengine-mcp"]`) that would install the frozen version as a *long-running server*.
`skills/` now has zero references to the frozen name. This was strictly worse than the
`.claude/settings.json` line in section E, and was found only because an agent obeyed the docs
literally.

**F2. `~/Projects/SCORE.md` was written by THIS build — a real gap in section B's fix.**
`findProjectRoot()` fell back to returning the starting directory when no `.git`/`package.json`
was found anywhere above, on the reasoning that *"an un-versioned directory is still scoreable —
it just scores badly."* That is the session-20 mistake wearing new clothes. Run from
`~/Projects` — a **container** of 37 projects, not a project — it scored the container and
wrote `Projects: 27/100 (F)` into it. Run from `/` it would do the same to the filesystem root.

Fixed with LOCK `[SCORE-CWD-MUST-BE-A-PROJECT]`: `findProjectRoot` returns `null`, and the
caller refuses with the three things the user can actually do (cd, name it, `--all`). Verified
from both `~/Projects` and `/`: exits 1, writes nothing.

The review was killed before it reported, so its remaining findings are unharvested — but it
had already paid for itself twice over. **Note for next time: subagents told to exercise a CLI
must be sandboxed, or told which flag makes it read-only.** The instruction "run the real CLI"
against a tool whose default writes to 37 repos is the same class of mistake as the default
itself.

## Lesson

Session 20's rule was *absence must never be encoded as a decision*. This session found the same
shape **three** more times, none of them in the scorer itself — all at the edges, where nobody
had thought to look:

1. a lookup that reported "not found" for a directory it never inspected (section C);
2. a **default that encoded "you didn't tell me which project" as "so I'll write to all 37"**
   (section B);
3. a fallback that encoded "there is no project here" as "so I'll score this directory anyway"
   — written *in the fix for #2*, the same hour, by someone who had just read the rule (F2).

An unspecified scope is an unknown, and the safe reading of an unknown scope is the smallest
one, not the largest. #3 is the instructive one: knowing the rule did not prevent applying its
opposite, because the fallback *felt* generous rather than presumptuous. The tell is not the
sentiment but the shape — any `return <something plausible>` in a branch that means "I could not
determine this" is the bug, however reasonable the something looks.

The corollary the hook report supplies: a defect that cannot be reproduced must not be fixed on
faith. Changing the hook template to "stop re-staging SCORE.md" would have produced a
convincing commit message for a line of code that never existed, and left the real cause — the
fleet-wide default — in place.
