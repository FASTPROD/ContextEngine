## 2. How it is wired today, and three things the prompt did not know

- `main()` (`src/index.ts` 1368 to 1585): register in the registry, parse sources, collect ops,
  auto-import learnings, inject learnings and the last session, connect stdio, then `loadCache()`;
  on a hit the vectors are used and `initEmbeddings()` is **never called**; on a miss the model
  loads and everything is embedded and `saveCache()` rewrites the single cache file. Then
  `startWatching()` puts one `fs.watch` on every source (820), debounced 500 ms, and every change
  calls `reindex()`, which does all of the above again and, if the model is loaded, re-embeds
  every chunk.
- **The cache misses by construction.** Its key is one SHA-256 over every chunk (`source`,
  `section`, `content`) of the whole corpus, and the corpus contains one ops chunk per project
  with `git diff --stat HEAD~1..HEAD` and the branch, the learning chunks, and the last session.
  A commit in any of 40 projects, a saved learning, a saved session, or another server with a
  different corpus writing the same file makes the key stale. Hence 2 hits in 51 starts. The
  file is one slot for a machine that runs three corpora (see below).
- **A warm-cache server has no semantic search and never re-embeds.** With the cache hit,
  `embedPipeline` stays null, so `vectorSearch` returns nothing, hybrid falls back to keyword,
  and `reindex()` skips embedding because `isEmbeddingsReady()` is false: that server keeps the
  old vectors paired with the old chunks for its whole life. Rare today only because the cache
  never hits. Worth a LOCK when the cache is rebuilt.
- **Three corpora on this machine, not one.** A server started in this repo reads
  `contextengine.json` here (explicit sources, workspaces, `codeDirs`: 4,464 chunks). A server
  started in any other cwd finds no config and auto-discovers `~/Projects` plus Claude memory
  (2,671 doc chunks plus ops and learnings). The launchd server runs from `~` with
  `OPSCONTEXT_SKIP_CLAUDE_MEMORY=1`: 105 sources, 2,611 chunks. Any shared index has to be keyed
  by what produced it.
- **The launchd server serves nobody and is starved.** stdin is `/dev/null` (no MCP client can
  ever connect to it), port 7842 was taken by a Claude Code server that started first (the
  browser-event ingest binds first-come), and its plist says `ProcessType Background`, which is
  macOS low CPU and I/O priority: 2.5 s of CPU in its first 15 min, 4.5 min from exec to
  `main()`, still on `Embedding 2611 chunks` with no progress line. Today it exists to keep a cache
  warm that never hits. Under any single-indexer design it is the natural standing indexer, but
  only with `ProcessType Standard` and the same corpus as the chats.
- `src/http-server.ts` serves two routes on 127.0.0.1:7842: `POST /events` (browser and VS Code
  audit events, shared-secret auth, `browser.*`/`vscode.*`/`cli.*` kinds only) and
  `GET /health`. Nothing reads the index through it. Its client is the browser extension.
- `clearCache()` in `src/cache.ts` is still dead code (SESSION_23).
- `chunk.contentHash` (16 hex of the content) already exists on doc chunks and is used only for
  dedup in `ingest.ts`.
- Wiring correction to `docs/AGENT_RULES_CE.md` § 7: the user-scope Claude Code entry in
  `~/.claude.json` now points at `/Users/yan/Projects/ContextEngine/dist/index.js` (the repo
  build), not the published package. The VS Code entry (`.vscode/mcp.json`) and the plist point

## 3. Options

Two costs multiply today: (i) a doc change re-embeds every chunk, and (ii) N servers each do it.
Any option below should first fix (i), because it is the larger factor and needs no election:

**Step 0, in every option: content-addressed per-chunk embedding cache.** Key = SHA-256 of the
exact text embedded (`section\ncontent` sliced to 512 chars); value = 384 float32. One
append-only binary file in `~/.contextengine` (record = 16-byte key + 1,536 bytes; the current
4,341 vectors fit in 6.7 MB, loaded in tens of ms). A doc change then embeds only its new chunks
(tens, not 4,464); a cold start on a machine that has embedded before hits for every unchanged
chunk, whatever the cwd, because the key does not depend on the corpus. This alone cuts the
embed CPU of every server by about 99% per change with today's N servers, and replaces the
single-slot 36 MB JSON. `cache.ts` goes; a LOCK carries its WHY.

| | (a) Leader on a lock, followers load the cache and never watch | (b) launchd is the indexer, MCP servers are thin clients over HTTP or a socket | (c) Shared on-disk index with a version stamp, readers reload on change, writer chosen as in (a) |
|---|---|---|---|
| What the user installs | Nothing | The launchd agent (`install-autostart`, macOS only today), with its plist changed to `ProcessType Standard` and the chats' corpus | Nothing |
| One chat, no launchd | The chat is the leader; behaves as today | No daemon: either every server falls back to today's code (two code paths to keep alive) or the first server spawns a detached daemon by the back door, which the prompt rules out | The chat is the writer; behaves as today, plus step 0 |
| Indexer absent or dead | The next server takes the lock at its next check; one re-index | Every tool answers nothing until the daemon is back, or falls back | A reader that finds no index, or a stamp whose writer pid is dead, indexes itself: the fallback is today's code path, not a second one |
| What a reader still does | Parses 820 files itself at start (vectors come from the cache, but chunk text does not; the cache stores keys only), then has no way to learn of a change without watching | Nothing but RPC; 35 MB, no model | Reads chunks and vectors from the index (about 10 MB, well under 1 s), loads the model lazily on the first semantic query (309 MB, 1.9 s) |
| Cost per doc change | 1 parse + step-0 embed + cache write; readers stay stale until their own next start | 1 parse + step-0 embed in the daemon; clients see it at once | 1 parse + step-0 embed + atomic index write; N readers reload in-process, under a second each |
| Memory, 10 servers | About today's | About 0.5 GB plus one daemon | About 0.4 GB while readers stay keyword-only, plus 300 MB per reader that has answered a semantic query |
| Learnings store writers | Leader only (auto-import); readers still write `save_learning` | Daemon only | Writer only; readers still write `save_learning` |
| What breaks | Readers answer from a stale index between restarts | 22 tools become network calls; the activation gate, sessions and learnings all move behind the socket; largest change by far | Nothing new: a reader without an index is today's server |

Corpus identity for (a) and (c): a short hash of what `loadSources()` and `loadProjectDirs()`
resolved from (config path and content hash, workspaces, patterns, `codeDirs`,
`CONTEXTENGINE_WORKSPACES`, `OPSCONTEXT_SKIP_CLAUDE_MEMORY`). One writer per corpus id. On this
machine that is three writers today instead of eleven; unifying the launchd corpus with the
chats' corpus (the `SKIP_CLAUDE_MEMORY` decision is Yan's) brings it to one.

Writer election for (c), no new lock file: the registry already holds pid, start time, build
hash and heartbeat for every server (`[SERVERS-ARE-INVENTORIED]`). Among alive records with my
corpus id, prefer servers whose build equals the file on disk (a stale build never leads: that
is the SESSION_25 incident), then the earliest start, then the lowest pid. Every server
re-evaluates every 15 s. Two servers starting in the same second may both index once; the index
write is temp file plus rename, so the last one wins and both readers stay consistent. The
registry record gains `role: indexer | reader` and `corpus`, shown by `contextengine servers`.

### Recommendation, five lines

Step 0 first, then (c) with the writer chosen from the registry. Step 0 removes about 99% of
the embed CPU on day one for every server, needs no election and no install. (c) then makes a
doc change cost one parse and one small embed, with readers reloading a 10 MB file instead of
re-running the pipeline, and a lone chat or a machine without launchd is simply the writer,
running today's code. (b) is the only option that also removes the 300 MB model from each
reader, but it turns every tool into RPC and leaves a daemon-less machine with nothing; not now.

### Step 0: `src/embedding-store.ts`, LOCK `[EMBEDDINGS-ARE-CONTENT-ADDRESSED]`

`~/.contextengine/embeddings.bin`: 16-byte header (`CEEMB001`, dims), then fixed 1,552-byte
records (16-byte key = SHA-256 of model + the exact embedded text, 384 float32). Append-only,
one write syscall per batch; a torn tail is cut before the next append and ignored by the
loader; a file that is not ours is refused whole. `embedChunks(chunks, store)` in
`src/embeddings.ts` looks every chunk up first and embeds only the misses, in input order, then
appends them. The indexer compacts the file (temp + rename) when it holds more than 10,000
records and more than twice the live ones. `src/cache.ts` is deleted; the LOCK carries its WHY
(2 hits in 51 starts, and a hit used to mean "no model, no semantic search, no re-embed ever").
Every server now calls `initEmbeddings()` when it embeds; a reader of the shared index defers
it to its first semantic query (300 MB and 1.9 s per process are worth waiting for).

### Option (c): `src/shared-index.ts`, LOCK `[ONE-INDEXER-MANY-READERS]`

- `corpusId()`: hash of the resolved config path and content, `CONTEXTENGINE_WORKSPACES`,
  `OPSCONTEXT_SKIP_CLAUDE_MEMORY`, home. Same id, same index; different id, own writer.
- `electIndexer()`: among live registered servers of the corpus, current build before stale,
  then earliest start, then lowest pid. A server missing from the registry indexes on its own.
- `writeSharedIndex()` / `readSharedIndex()`: `~/.contextengine/index/<corpus>.json` with seq,
  stamp, writer pid, sources, project names, chunks and one store key per chunk; temp + rename;
  a reader refuses a half-shaped file. `sharedIndexMtime()` is the reader's 3 s stamp check.
- `src/index.ts`: one `buildIndex()` for start and reindex (the two copies were merged),
  `embedAll()` through the store, `publishIndex()` (indexer), `adoptSharedIndex()` (reader),
  `evaluateRole()` every 15 s with promotion (model, reindex, watch) and demotion (stop
  watching, poll). Readers never watch files and never run the learnings sweep. The `reindex`
  tool on a reader reloads the shared index and names the indexer.
- Registry: `corpus` and `role` per record, `setRole()`, printed by `contextengine servers`;
  the "too many servers" warning now counts only servers that index on their own. Audit events
  `server.role`, `index.write`.

## 2026-09-06 morning: "search_context and score_project fail with a JavaScript error"

Reported from another chat (save_learning worked, the rest did not; not chased there). Chased
here: reproduced on a reader from invoc.io with the flag on, with the flag off, and against the
published 2.5.9 from a temp cwd, so not tonight's code. Cause: 20 agent-saved records in the
store (`s57_*`, `s78_*`, kept on purpose in the SESSION_25 prune) have no `tags` array, and
`searchLearnings` did `learning.tags.join(" ")`. That call sits inside the firewall's learning
injection, which runs for every tool that passes a context hint (search_context, score_project),
so those answered "Cannot read properties of undefined (reading 'join')" on every server, while
exempt tools (save_learning) worked. Fix: read with fallbacks, LOCK
`[LEARNING-FIELDS-ARE-OPTIONAL-ON-READ]` in `src/learnings.ts`, the two other `tags.join` sites
(`index.ts`, `cli.ts`) guarded, regression test in `src/learnings-store.test.ts`; the 20 records
are not touched. Verified: both tools answer on a reader spawned from invoc.io.

Two things learned on the way:
- The running servers hold the old code until their windows restart, so the fix reaches a chat
  only after a reload; `contextengine servers` says STALE BUILD for all eight until then.
- Election side effect, by design: after a build every running server is stale, so any
  short-lived process on the new build (my probes) wins the indexer role for its lifetime and
  the previous indexer demotes to reader, then promotes itself back at the next 15 s election
  with one reindex. Harmless (a reindex is one parse and a few embeds now), and it is exactly
  what protects the store from a stale importer; noted so nobody reads the churn as a bug.
