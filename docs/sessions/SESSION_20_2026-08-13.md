# Session 20 — 2026-08-13 — Absence is not a verdict: canary, invariants, and a dead backup

**Scope**: applied an external critique of guard-writing to CE. The critique's ranking — canary first, arithmetic invariants second, named guards third, hooks last, and above all *"absence must never be encoded as a decision"* — turned out to describe four live bugs in CE's own scorer, one of which had been silently breaking CE's Google Drive backup.

## Trigger

User relayed an agent's argument that guards are "a museum of past mistakes" and asked: *"what can you apply to our CE?"* Then: *"yes proceed as recommended."*

## The finding that justified the whole exercise

Applying the deepest rule to CE found a live failure within ten minutes.

`hooks/post-commit` was deleted by [`56ef658`](../../hooks/post-commit) (2026-06-10, *"chore(hygiene): P0 truth alignment + cleanup pass"*). The `.git/hooks/post-commit` symlink kept pointing at it — dangling. `existsSync()` follows symlinks, so CE's own scorer reported:

```
| Git hooks | Infrastructure | 0 | 5 | ❌ | No hooks — consider auto-push |
```

Three distinct states collapse into that one row: never configured, configured-and-broken, configured-but-unreadable. They need different actions, and the row named the wrong one. Meanwhile the Drive backup silently stopped receiving commits.

**Severity correction made mid-session:** I first reported the Drive backup as empty. It was not — the bare repo's `HEAD` points at `master` (no commits) while the content lives on `main`, at `9340773` from 2026-06-27. Four commits stale, not dead. Real bug, smaller blast radius than I first said.

## What was done

### A. Backup restored

Recovered the canonical hardened hook (the `GDRIVE_REF_SELFHEAL` version from `STRIPE backend`, which carries the 2026-07-13 Drive duplicate-ref self-heal). Installed at `.git/hooks/post-commit` as a **real file, not a symlink**, with a new LOCK `[POST_COMMIT_REAL_FILE]` explaining why the indirection is banned here. Tracked reference copy restored at `hooks/post-commit`, matching `hooks/pre-commit` and `hooks/commit-msg`. Drive backup caught up: `9340773..645978a`.

Fleet scan for the same class found: `invoc.ch` and `COMPR` have a `gdrive` remote but **no post-commit hook at all**, and `FASTPROD`'s Drive bare repo is **empty**. Left untouched — other people's repos, flagged to the user rather than fixed unilaterally.

### B. `unknown` status + the provenance rule — LOCK `[ABSENCE-IS-NOT-A-VERDICT]`

`ScoreCheck.status` gained `"unknown"`: 0 points, rendered ❔, and listed under a new **"Could Not Be Verified"** section — deliberately *not* under "Improvements Needed", because it is a gap in the audit, not a defect in the project. Rule enforced: every pass/fail detail must name what was inspected.

Live offenders fixed:

| Check | Before | After |
|---|---|---|
| `Git hooks` | `"No hooks — consider auto-push"` for a dangling link | distinguishes absent / installed / **BROKEN — dangling symlink**, naming the target |
| `Secrets exposure` | **6/6 ✅** `"No .env or not a git repo"` | splits into pass (genuinely no `.env`) and `unknown` (can't verify) |
| doc checks | `"Missing"` | already fixed in S19; the general rule now covers them |

### C. Arithmetic invariant — LOCK `[SCORE-ARITHMETIC-INVARIANT]`

Several checks only emit inside an `if` (`Deps gitignored` needs a `.gitignore`; `npm scripts` and `Lockfile` need a `package.json`). A skipped check silently **shrank the denominator** — a project was scored out of 94 while every report and every cross-project comparison presented it as out of 100. Nothing looked wrong on screen; the number was just quietly measuring something else.

The denominator is now pinned to 100. Any shortfall becomes a visible `Scoring completeness` unknown row worth the missing points, plus one stderr line (never stdout — MCP protocol stream). Exact, free, unarguable, every run.

### D. The canary — LOCK `[SCORE-CANARY]`

`runScoreCanary()` builds a synthetic project **at runtime** (so it ships with the code rather than as an unpublished test fixture) containing every awkward case at once: doc at repo root, doc in `.github/`, dangling hook symlink, `.env` with no git repo, no package manager. It scores it and compares against a pinned expectation. `cliScore()` runs it first and **refuses to write a single SCORE.md** on any deviation. A fixture that cannot be built returns `inconclusive: true` and still blocks — an unverified scorer is an unknown, never a pass.

**It found a bug on its first run.** Not the bug it was written for — an unrelated one.

### E. What the canary caught — LOCK `[EXEC-FAILURE-IS-NOT-EMPTY]`

`exec()` returns `""` on *any* failure: command not found, not a git repo, timeout, permission denied — indistinguishable from a successful empty result. The `Secrets exposure` check ran `git ls-files .env`, got `""`, concluded ".env is not tracked", and awarded **6/6 PASS**.

A security check that hands out full marks precisely when it cannot verify anything is worse than one that fails — it manufactures reassurance. Fixed with `execChecked()` returning `{ ok, output }`; security-relevant callers emit `unknown` when `ok === false`.

This is the same shape as `existsSync()` following symlinks. Both are stdlib functions whose "not found" answer quietly absorbs "could not look."

### F. Release 2.2.0 — staged, blocked at the last step

De-flaked `tests/cli.test.ts` first, and the defect there was the session's own theme: `run()` converted a timeout into `""`, so a killed process surfaced as `expected 0 to be greater than 0` instead of `SIGTERM`. Now it throws with the signal and timeout; the search test gets 60s because it legitimately loads the local embedding model (~2s standalone, longer under parallel suite load).

Bumped 2.1.3 → **2.2.0** (minor, not patch: `unknown` is a new status and the canary now blocks writes — behavior users will feel). Both CLAUDE.md rule 9 smoke tests pass: `search "test"` returns ranked results, `score ContextEngine` writes SCORE.md at 93%.

`npm publish` was then **refused by CE's own pre-publish guard**:

```
✗ npm publish token has expired — refusing to publish.
  token : compr-scope-publish-2026-06
  expiry: 2026-07-11  (33d PAST)
```

Working as designed. Commit `badc0af` is pushed; the `v2.2.0` tag is held **local only** so a tag never claims a release that isn't on npm. Token rotation is the user's to do.

**Noted, not fixed:** CLAUDE.md rule 3 says `agents.ts`, `collectors.ts`, `search.ts` "must never be included in npm publishes." They are — verified by unpacking the published 2.1.3 tarball, which contains 75KB of real `dist/agents.js`. This predates 2.2.0, so the release doesn't worsen it. It looks like the model deliberately shifted (see `56ef658`: collectors moved out of `PREMIUM_MODULES` because it runs for every user, with the PRO *tools* remaining activation-gated) and rule 3's wording never caught up. Needs a decision: reword the rule, or actually exclude the files.

### G. Fleet backup repairs

| Repo | Found | Done |
|---|---|---|
| `invoc.ch` | no post-commit hook, 1 commit unbacked | hook installed, pushed |
| `COMPR` | no post-commit hook, 5 commits unbacked | hook installed, pushed |
| `FASTPROD` | hook present but **bare repo corrupt** | repaired, pushed |

**Two corrections to what I reported before checking properly.** The alarming Drive dates (`invoc.ch` at 2026-03-22, `COMPR` main at 2025-09-03) are last *commit* dates, not last *push* dates — those repos simply hadn't been committed to. And FASTPROD's Drive repo was not "empty"; my `for-each-ref` read was wrong.

FASTPROD was the real problem, and a different one than advertised: `refs/heads/main` pointed at `72d6ece`, an object absent from the bare repo, so every push died with `pack has 13 unresolved deltas`. `--no-thin` couldn't help — git can't compute a delta against a ref it can't read. Classic partial Google Drive sync.

Repair was minimal rather than a re-seed: a *loose* `refs/heads/main` (dangling) was shadowing a *packed* `refs/heads/main` at `b0741b9`, and that commit was intact in both the bare repo and locally. Deleting only the loose file let the valid packed ref take over, after which `b0741b9..48bf416` pushed cleanly and `fsck` came back silent. Nothing recoverable was destroyed — the deleted ref pointed at an object that did not exist, and its value is recorded here and in the transcript.

All four repos now: hook present, 0 commits unbacked.

## Lesson

The critique's ranking held up exactly as stated. The named guards I wrote in Session 19 caught nothing new — they can't, they're shaped like the bugs that already happened. The canary caught a bug in its first execution, in code nobody was looking at, because it doesn't ask "is the known defect back?" but "does every signal still read as pinned?"

And the deepest rule earned its place: four separate bugs, one shape. `existsSync()` conflating dangling with absent, `exec()` conflating failure with empty output, a skipped check conflating "not assessed" with "smaller exam", and a score row conflating "couldn't check" with "fine". Each one produced a plausible number that pointed at the wrong fix. CE already had this rule for *findings* — a count is not reportable until the tool prints its provenance. It had simply never been applied to plumbing.
